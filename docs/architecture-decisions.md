## D01 · 网关（Web Server）与 Chat Server（Joker）角色切分

**背景**：原 brave 中 server（`brave start`）是 HTTP API，joker 持有 WebSocket。设计早期曾把 Joker 误定位为"接入层网关"——被用户纠正：Joker 的原设计就是 Chat Server，Web Server 登录后返回 `login_host` 本来就是网关行为的雏形。

**决策**：Web Server = 网关（统一 REST 入口、鉴权、`/v1/feed/*` 路由、经 etcd 选点下发 `ws_addr`）；Joker = 哑 Chat Server（连接生命周期、收发、gRPC 收投递）。WS 数据面**不经过网关**。

**理由**：网关无状态可水平扩展；网关若转发长连接即成为吞吐瓶颈与单点；Joker 保持零状态管道，群语义终结在 Delivery Worker。

**代价**：客户端需要两阶段接入（先 REST 登录拿 ws_addr，再 WS 直连）；跨网络环境（防火墙只放行 443）需要额外 TCP/WS 代理层。

**教训**：v1 设计文档曾把角色弄反——架构文档的角色命名必须与代码的历史语义对齐，不能为了图表好看重排职责。

**重评触发**：需要端到端 mTLS/统一限流时，可考虑 WS 也收编进网关（L7 代理模式），代价重新评估。

## D02 · 消息主干走 Kafka，而非 Joker 间直连 gRPC

**背景**：AGENTS.md 原计划（参考 gowebsocket）：Joker-A 的 SendMessage 查到收信人在异地 → 直连 gRPC 转发。这是最短路径。

**备选对比**：

| 方案 | 时延 | 正确性 | 削峰 |
|---|---|---|---|
| CS 直连 gRPC（原计划） | 最低（1 跳） | 投递先于持久化 → 幽灵消息 | 无 |
| Kafka 主干（选定） | +2 跳（P99 +~20ms） | 先落库后投递，推出必已存在 | 有 + 可回放 |

**决策**：CS 只 produce `chat.msg`；落库（persist）→ `chat.push` → 投递（deliver）全部经 Kafka。

**理由**：投出去的消息必然已落库，通知与库永不分叉；顺序由分区保证（chat.msg 按 conv_id/gid、chat.push 按 to_uid 两个顺序域一次扇出完成切换）；失败可重放、削峰垫背；练手规模时延余量巨大（估算端到端 P99 50-80ms，IM 阈值内）。

**代价**：多两跳时延；链路组件多（运维面变大）；调试时消息"在途"状态不可见（要靠 lag 监控）。

**重评触发**：产品要求在线投递 P99 <20ms 且接受弱一致 → 回到直连模式（gowebsocket 原教旨），并补"幽灵消息"对账。

## D03 · 投递推完整消息，非 notify-pull

**背景**：deliver 投递时两种模式——A：chat.push 带完整 body，gRPC 带货直达；B：只发轻通知 (uid, seq)，目标 CS 回源拉取再推。

**决策**：当前推完整消息（A）；群聊规模触顶后先切群聊轻通知（B 变体 1），远期全量 notify-pull（B 变体 2）。

**理由**：A 链路短、CS 零状态、当前容量（600 TPS 峰值）余量 2 个数量级——B 解决的瓶颈现在不存在。B 的真正收益：扇出流量从 O(在线成员数×body) 降为 O(通知条数)、在线/离线补齐统一为一条读路径、弱网断点续传友好——这些在"单群在线 >200 / 扇出占 Kafka 带宽 >10% / 弱网补拉高频"时才兑现。

**代价**：A 模式 500 人群一条消息在 Kafka 里重复存 ~500 份 body（lz4 压缩部分缓解）；B 模式 CS 状态化 + 需要回源缓存层 + seq 对账通道。

**关联**：无论 A/B，D15（seq 对账）都是必备兜底——它比模式选择更优先。

## D04 · PostgreSQL + pgx，弃 MySQL + jinzhu/gorm

**背景**：技术栈要求迁移 PG 且 PG 兼作 KV。当前 brave 用 jinzhu/gorm v1（已停止维护）+ MySQL。

**决策**：PG 15 + pgx v5（手写 SQL）+ goose v3（postgres 方言）。

**理由**：设计重度依赖 PG 特有能力——JSONB（kv 表、messages.content、@ 结构）、COPY 批量写（feed_inbox 500/批、群聊扇出）、事务内原子自增（`seq:{conv}`）、LISTEN/NOTIFY（路由失效加速）。这些在 ORM 里都要退回 Raw SQL，等于两套心智模型并存；pgx 是 PG 事实标准驱动（wire 协议优化、pgxpool）。

**代价**：失去 ORM 的 CRUD 映射与迁移工具生态；SQL 全手写（练手项目这反而是优点——每条语句可讲）。

**重评触发**：团队强偏好 ORM → gorm.io/gorm v2 + postgres driver 也可行，代价是特有能力全走 Raw。

## D05 · PG 兼作 KV，etcd 退回纯服务注册表

**背景**：当前 brave 把用户登录态也放 etcd（`users/{uid}`，无 TTL、宕机残留）。目标技术栈指定"PG 同时作为 kv store"。

**决策**：新增 PG `kv` 表（k TEXT PK, v JSONB, version, updated_at）承担 `online:{uid}` / `seq:{conv}` / `unread:{uid}` / `feedcur:{uid}`；etcd 只留 `services/{uuid}`（lease 60s + keepalive + watch）。

**理由**：写入路径全过 PG → 一处事务、一处备份（流复制/pg_dump），无跨存储一致性问题；etcd 回归单一职责（服务表几十条，正是它设计的目标负载）。

**代价**：kv 高频读需要 30s 进程内缓存；PG 单点成为更多链路的公共依赖（好在已有 1 主 2 从）。

**重评触发**：kv 读 QPS 打满 PG（缓存命中率崩） → 引入独立 KV 缓存层（Redis/DRAM），仅作读穿透，权威仍在 PG。

## D06 · 在线路由放 PG kv，拒绝 etcd 方案

**背景**：用户提议：online:{uid} 交 etcd（lease+watch），Joker/Worker 直接消费。机制上与服务发现同构，当前 brave 原始设计即此思路。

**分析（失效地狱）**：N 个消费方各缓存一份路由 + 靠 watch 事件失效——事件通道不保证不丢不滞后不断线；etcd 1h compaction 后 watch 重连必须全量重建（10 万在线 = 10 万 key 重拉 × 5 订阅方）；多副本事件乱序使"投错节点"不可排查。本质：用"事件最终同步"维护 N 份状态副本，却没有权威兜底告诉副本"你错了"。

**决策**：权威单点 PG kv + 三道防线——① Worker 缓存 TTL 上界 30s（过期有上界，不依赖事件）；② 投递 not-found 即时校正（投错 → 强制查权威值重投，错误视图存活 = 一次失败投递）；③ LISTEN/NOTIFY 仅加速不担责。路由副本方全系统仅 Worker×2（Joker 只查本机 sync.Map，不碰全局路由）。

**代价**：路由查询多一跳 PG（30s 缓存摊薄）；GHOST 清理需要独立对账任务（60s 周期）。

**何时 etcd 是对的**：在线主体是实例级（几百个）、无 PG、规模万级以下——lease+watch 优雅且够用。地狱是规模的函数。

## D07 · 好友关系不上图数据库

**决策**：friends 留 PG（PK(owner_uid, friend_uid) 双边存两行）。

**理由**：访问模式只有三种 1 度查询——双边判定（PK 点查）、好友列表（uid 索引）、fanout 取 UID 列表（一次范围扫描）。图数据库的不可替代性在多跳遍历（共同好友/二度推荐/路径），本项目一个都没有；100 万行边表对 PG 是零压力量级；好友变更与 users/会话需要同事务域；3 台机器多背一个 Neo4j 换零收益。三段式：数据形态 → 访问模式 → 存储选型。

**重评触发**：出现 2+ 度遍历成为核心功能，或边表亿级且 fanout 读 P99 超标 → friends 边表离线同步到图库（好友关系容忍秒级延迟，无需强一致双写）。

## D08 · 群聊：投递层写扩散、存储读扩散

**背景**：约束②要求"写扩散"，群成员 ≤500。

**决策**：persist 落库 1 份（存储不扩散）→ 批量查 online kv → 仅对在线成员 produce chat.push ×M（投递写扩散）。离线成员不扇出不标记，上线按 seq 游标拉取。

**理由**：聊天语境"写扩散"的收益在推送及时；存储扩散的收益在未读数/读时聚合——本项目明确不做未读数（D10），存储扩散只剩 500 倍写放大没有收益。500 在线成员扇出 = 500KB/条，容量账（D13）内余量充足。

**代价**：投递写放大（260 万 push/天）；同一条消息体在 Kafka 重复 M 份。

**重评触发**：单群在线 >200 或扇出占带宽 >10% → 切 D03-B 变体 1（群聊轻通知+自取）。

## D09 · 群事件即消息

**决策**：踢人/改名/公告/置顶/解散等管理操作在事务里同时 ①改 groups 表 ②INSERT 一条 `type=system_event` 消息 → 走同一条 persist→push 链路扇出。

**理由**：成员打开会话即见事件（"xxx 把 xxx 移出了群聊"），事件与普通消息共享 seq 流天然保序；不需要发明第二条通知通道；解散后 persist 拒收该 gid 一切后续消息，状态收敛简单。

**代价**：events 语义混入 messages 表（type 区分）；置顶/公告是"状态+事件"双写（以表为准，消息只是通知）。

## D10 · 未读数 / 已读 / 撤回明确不做

**决策**：约束③④，明确不做并在 README 标注。

**理由**：已读矩阵是 N×M 写入（最贵的状态）、撤回要处理已投递消息的回溯删除（跨端一致性）；砍掉它们才敢在 3×4C16G 混部上跑群聊。客户端可用本地 last_seq 自行渲染红点。

**代价**：产品完整性缺口（微信用户预期这些功能）；未来补做时已读矩阵需要独立表 + 批量聚合，撤回需要 tombstone + 端端协议。

## D11 · persist/deliver 拆分部署，双实例跨节点

**背景**：曾设计单"Delivery Worker"进程承载落库+投递两组消费者。质疑：会不会瓶颈？会不会单点？

**分析**：容量不是问题（落库 120 TPS vs PG 1-3 万；投递 600 TPS / 12 分区 = 50 TPS/分区，消费组天然并行）。真实问题是**共享 PG 连接池**：PG 抖动时 persist 慢查询打满连接池，deliver 的路由查询被连带饿死。

**决策**：同一代码库拆两个部署单元（persist-worker / deliver-worker），各 ≥2 实例跨节点，消费组 rebalance 自动接管；扩展路径 = 加实例 → 加分区，与节点拓扑解耦。

**代价**：部署单元从 1 变 2（supervisord/compose 条目多一项）。

**教训**：v3 曾只画单实例——容量够 ≠ 可用性够；数据不丢（Kafka 兜底）≠ 服务不中断（投递延迟）。双实例纯为高可用。

## D12 · 离线通知：deliver 判定副产品驱动

**背景**：用户提出"Joker 判定在线/离线：在线直投、离线交通知系统"——业务需求正确，但判定智能放 Joker 会破坏 D01/D02/D06（Joker 需要全局路由 = 失效地狱 +N；直投 = 幽灵消息）。

**决策**：离线判定放在 deliver 查路由那一刻（查不到 online = 离线，**零额外查询**）→ produce `chat.notify`（不含原文）→ Push Worker 独立消费 → APNs/FCM/厂商通道。节流（60s 同人合并/夜间静默/频控）全在 Push Worker，不污染主链路。

**理由**：通知通道慢/挂不影响 IM 收发；通知内容不含原文（隐私 + 点击免登拉取）。

**代价**：离线用户感知依赖厂商通道到达率；通知时延 = 主链路 + 通道（秒级）。

## D13 · 容量口径：DAU 1 万推导链（含两次口径修正）

**假设**（拍脑袋，待压测校准）：DAU 1 万 / 人均 50 条 / 群聊占 30% / 均群 50 人 / 在线率 30% / 峰值系数 ×20（业界 3-10，取 20 保守包络）/ 消息 1KB。

**推导**：总量 50 万条/天 ≈ 平均 6 TPS；persist 峰值 = 120 TPS（存储不扩散）；投递 = 35 万单聊 + 225 万群扇出 = 260 万 push/天 → 峰值 600 TPS；离线通知峰值 ~180 TPS。

**修正记录**（审计中发现并已改文档）：① 曾误写 persist 峰值 "150 = 120+26"——120 已是全量、26 是群聊 push 平均，口径混叠，正确值 120；② "520 TPS" 只是群聊扇出部分，全量口径 600（单聊 81 + 群聊 520）。

**用法**：这些数字的正确用法不是"系统容量是 600"，而是"假设错 10 倍系统也不塌"（各环节余量 2 个数量级）。真实容量等 kernel-tuning.md 压测闭环产出，尤其要校准 ×20 系数。

## D14 · 心跳：客户端主动上报 + 6 分钟超时清理

**决策**：客户端 30s 应用层心跳（携带 seq 游标，见 D15）→ CS 只更新时间戳 → 定时任务清理 6 分钟无心跳连接（参考 gowebsocket `heartbeatExpirationTime = 6*60`）。

**理由**：服务端被动模式比每连接 30s 主动 ping 省 CPU 一个量级（百万连接场景 3.3 万/s ping-pong 全免）；brave 现有 `ticker 1ns` bug 的正确修法就是这个模式（AGENTS.md §2 已锚定）。

**代价**：离线检测延迟最坏 6 分钟（通知系统 D12 补位感知）。

## D15 · 客户端 seq 对账兜底

**决策**：客户端心跳携带 `{conv_id, last_seq}`，CS 比对最新 seq，发现 gap → 触发补拉。

**理由**：这是推模式（D03-A）与拉模式（D03-B）**共同的终极兜底**——任何丢推、乱序、重连、dlq 漏网都能自愈；它让 D06 的"事件可丢"和 D03 的"通知可丢"从缺点降级为可接受代价。

**代价**：心跳 payload 变大（活跃会话列表）；CS 心跳处理增加一次 seq 比对（可批量缓存）。

**优先级**：排在所有投递模式优化之前——先有对账，才谈得上砍通道。

## D16 · messages 暂不分区 + conv_id 采用雪花 ID（推迟决策）

**背景**：分区存在两难——按 created_at RANGE 归档语义正确，但 PG 要求 UNIQUE 约束含分区键，`UNIQUE(conv_id, seq)` 全局唯一做不到（D08 的幂等防线降级）；按 conv_id HASH/RANGE 可保留唯一约束，但归档语义错位（老会话的新消息永远落旧分区，DROP 会误删活跃会话数据）。多级分区（时间主 + conv HASH 子）可两全但运维复杂，判定为当前规模过度设计。

**决策**：① messages **暂不分区**，`UNIQUE(conv_id, seq)` 全局有效；② conv_id 采用**雪花 ID**（唯一 + 趋势递增，workerId 三节点静态分配 0/1/2，时钟回拨保护），为未来按 conv_id 分区留后门；③ 到触发条件再单边选择，不预先建分区。

**理由**：当前 90 天保留 ≈ 1.35 亿行 / ~70GB，单表舒适区；推迟决策成本为零，提前分区反而背上 UNIQUE 降级或归档语义受损的包衢。Kafka key=conv_id 用雪花不受影响（hash 打散无热点）。

**重评触发**：单表 >2 亿行；归档 DELETE 出现小时级阻塞/表膨胀；索引维护拖慢写入峰值。到时二选一：created_at RANGE（弃全局唯一，幂等改应用层）或雪花 conv_id RANGE（弃时间窗归档，改冷会话整体归档）。

## D17 · Kafka 分区数 12P 的由来

**决策**：chat.msg / chat.push 12P，feed.fanout 6P，chat.ack 6P，chat.notify 3P。

**推导**（诚实版）：单看目标 600 TPS 投递峰值，2-4 分区即够（单分区串行消费 500-800 TPS）。取 12 是四个理由叠加：① 扩容有 hash 重分布乱序窗口 → 宁多勿少，起步给足；② 3 broker 均分（12÷3=4 leader/broker）；③ 增长冗余（12P ≈ 7-9 千 TPS，覆盖 DAU 5-8 万，冲 30 万时 12→24P 是预谋内动作）；④ 消费实例并行度上限 12 与三机可部署实例数匹配。低量级 topic（ack/notify）不陪跑 12P。

**代价**：当前量级下略付元数据/rebalance 成本（可忽略）。

## D18 · 写操作归位无状态 worker 层，Joker 零写

**背景**：质疑——Joker 削薄到只剩「连接+produce」后，写全部压在 delivery worker，会不会有压力？前提纠偏：写操作从 v2 起就在 worker 层，不是 Joker 削薄后才转移的。

**决策**：落库事务只在 persist 消费组执行，Joker 永不直写 PG。

**理由**：① **故障隔离**——若 Joker 直写，PG 抖动会阻塞 Pump goroutine → 心跳起时 → 误判踢连接 → 连接层雪崩；现状里 PG 慢只表现为 chat.msg 堆积（Kafka 吸收），连接层无感。② **seq 单点串行**——chat.msg 按 conv 分区 → persist 分区单线程消费 → seq 自增无竞争；Joker 直写则同会话跨节点抢 seq（PG 行锁/分布式锁），吞吐与复杂度双输。③ **PG 连接收敛**——persist×2 连接池 vs N×Joker 连接池，连接数与长连接规模解耦。

**代价**：worker 成为写吞吐的责任层（加实例/加分区是它的扩展路径）；多一跳 Kafka（与 D19 同源）。

**关联**：D02、D11。

## D19 · 落库后经 chat.push 二次入队，禁止 persist 直投 gRPC

**背景**：质疑——persist 落库后为什么不能再走一次 Kafka，直接 gRPC 交给投递节点？诚实时延账：多一跳 P50 +2~8ms、P99 +10~20ms。

**决策**：persist 落库后 produce chat.push（key=to_uid），由 deliver 消费组投递；persist 不直接发起 gRPC。

**理由（四个结构性代价换不来的 10ms）**：① **顺序域切换**——conv_id→to_uid 在一次 produce 完成；直投则同一接收者的消息来自多个 persist 分区并发 gRPC，接收端乱序窗口常开。② **背压隔离**——投递慢/CS 抖动不阻塞落库循环；直投则 chat.msg 积压→落库停摆→历史空洞。③ **群聊扇出解耦**——500 次并发 gRPC 不该 persist 做（否则落库吞吐从 ~1ms/条劣化到 500ms/条量级）。④ **单一路径**——重试/dlq/lag 监控/D03 演进开关全部锚定 chat.push→deliver；直投 = 进程内自造重试队列 + 两条投递路径。

**代价**：多一跳时延；在途状态不可见（靠 lag 监控）。

**优化正道**：deliver 消费端 fetch 低延迟配置（fetch.min.bytes=1、短 poll）把第二跳 P99 压到 5ms 内——调参数不动架构。

**远期备忘**：极致时延的 fast/slow 双路径（在线直投+异步落库两路汇合去重），产品级需求才值得，练手不做。

## D20 · 顺序保证四环节 + 分区单 goroutine 红线

**背景**：Kafka 顺序机制追问。本质：Kafka 只承诺「分区内严格有序」；顺序保证 = key 路由同分区 + 链路每一环保持串行。

**决策/纪律（四环节守门）**：① producer——业务消息必带 key + `enable.idempotence=true`（防重试乱序，幂等不止防重也防乱）；② broker——`unclean.leader.election=false` + ISR（防落后副本当选截断日志）；③ consumer——**每分区单 goroutine 串行处理**，处理完才 commit（消费有序处理无序是顺序碎掉的最常见点，review 红线）；④ 目标端 FIFO chan（满则踢线不跳跃）。

**仍会乱的三情况备案**：分区扩容 hash 重分布（pause+drain 或接受 seq 兑底）；at-least-once 重放（重复≠乱序，UNIQUE 幂等去重）；有人改并行度（红线）。

**定位**：服务端机制的目标是让客户端 seq 兑底（D15）几乎不触发，而不是让它不必要。

## D21 · 不做演示集群，以实测数字为目标

**背景**：多轮极限推演——降级 Kafka/PG 为单点腾内存冲连接/DAU、纸面百万连接。数学结论：3×16G 总内存硬上限 ~94 万连接（零水位零冗余）、单点化现实 65-75 万；百万需 32G 接入机。DAU 30 万为边界可行，三前提：notify-pull 切换 + 12P→24P + 峰值系数实测替换（×20 是包络不是实测）。

**决策**：保持 3 节点 RF=3 全冗余标准混部；连接/吞吐目标 = 压测实测数字（单节点 10 万 / 集群 30 万 / 投递 600 TPS），不追纸面大数字。

**理由**：RF=1 演示集群无叙事价值且丢高可用（Kafka 单点=投递停摆，PG 单点=路由表全丢）；「3 节点全冗余 + 实测 X 万」比「单点 + 纸面 70 万」可信一个量级（AGENTS.md 诚实性原则）。

**代价**：放弃纸面大数字；极限路径仅作为备案（32G 接入机/notify-pull/24P）留在文档，不作为目标。

## D22 · MQ 选型封盘：Kafka 留任（heap 压缩），Redpanda 备忘

**背景**：JVM 内存顾虑引发的换道评估（RabbitMQ / RocketMQ / Redpanda / NATS）。

**决策**：Kafka 留任，混部场景 heap 压至 512M-1G（低吞吐下安全）；Redpanda 记入备忘——若实测内存成为真瓶颈，协议兼容零改造切换；RabbitMQ、RocketMQ 否决。

**理由**：RabbitMQ 省内存有限（~0.5-1G/节点）且要重开 D02/D03/D08/D11 四张决策牌（无分区键顺序语义、无 offset 回放、堆积触发流控反压生产者主链路）；RocketMQ 同为 JVM 且 broker 惯例 heap 4-8G+堆外写缓存，内存最重；Kafka 是唯一能把 JVM 开销压到很小的主流选项，pagecache 可回收不算硬占用。

**代价**：接受 JVM 存在（heap 1G 后顾虑基本消除）。

**教训**：选型讨论先分辨目标函数——吞吐/可靠性选型（RocketMQ 的主场）与混部省内存（Redpanda 的主场）是两个不同问题，不混谈。
