仿微信 IM + 朋友圈 — 目标架构设计

角色定位以原设计为准：Web Server（brave start）是网关层——统一 REST 入口、鉴权、服务路由，登录后下发 WebSocket 接入地址； Joker（brave joker）是 Chat Server——直接与客户端建立长连接，负责连接管理与消息收发。 在此骨架上演进为完整仿微信系统：聊天（单聊/离线/ACK）+ 朋友圈（push/pull hybrid 新闻流）。 存储迁移 PostgreSQL（JSONB kv 表兼作 KV），主干引入 Kafka，部署于 3 台 4C16G。
群聊（<500 成员 · 写扩散投递 · @ 与 @all · 群管理五件套）复用同一套链路，详见 §5；在线/离线状态管理与离线通知系统见 §4。
配套文档：全部设计权衡的决策记录见 docs/architecture-decisions.md；WS 长连接内核调优与压测闭环见 docs/kernel-tuning.md。

02总体架构

两条客户端通道：REST 全部经网关（Web Server）；WebSocket 按网关下发的 ws_addr 直连 Chat Server（Joker），数据面不过网关。控制面（etcd）仅服务注册发现。
Gateway（Web Server · REST 入口） Chat Server（Joker · WS 长连接） Feed API / Fanout Push Worker（离线通知） Kafka PostgreSQL（SQL+KV） etcd（控制面）

03聊天链路 · 接入与消息投递

接入（经网关）：REST 登录 → 网关经 etcd 选 Chat Server → 下发 ws_addr → WS 直连 → CS 维护 online kv。投递（Kafka 主干）：收→保序落库→扇出→gRPC→ACK。
接入握手 · 0a-0d（网关的入口职责）
0a. POST /login
Client → 网关：账号密码（bcrypt 校验，签发 token）
0b. 选节点
网关从 etcd 服务表（每 5s 刷新，复用现有 StartListenService）按负载/随机选一个 Chat Server
0c. 下发 ws_addr
响应携带 {ws_addr: "cs-2:37002", token}（即现有 login_host 机制的正式化）
0d. WS 直连
Client → Chat Server：GET /ws/:id 升级长连接；CS upsert online:{uid}={cs,addr} 到 PG kv
WS 通道（Client↔Chat Server 直连） gRPC 投递（Worker→Chat Server） Kafka PG 事务 ACK/成功
会话内顺序保证
  • Kafka 按 key=conv_id 哈希分区 → 同会话同分区，分区内严格有序
  • Persist Worker 单 goroutine 消费每分区；seq 由 PG kv[seq:{conv}] 事务内原子自增
  • messages UNIQUE(conv_id, seq) 双保险，重放不产生重复行
在线路由（PG kv · CS 维护）
  • WS 建立：Chat Server upsert online:{uid}={cs,addr}
  • WS 断开：CS 删 kv；宕机场景由对账任务兜底清理（lease 思路改在 PG 上实现）
  • 加分项：PG LISTEN/NOTIFY 广播路由变更，Worker 本地缓存 30s TTL
网关与 CS 的职责分界
  • 网关：鉴权、REST 聚合、选点下发 ws_addr —— 不接触消息数据面
  • Chat Server：连接生命周期、收发、投递接收 —— 不做跨节点路由决策
  • 跨节点路由统一在 Delivery Worker（查 kv + gRPC），单一位置可测试可观测

04在线状态与通知系统

路由权威单点 PG · Joker write-through · TTL 惰性失效 + not-found 兑底 + 对账清理。离线判定是投递查路由的免费副产品，顺势驱动 Push Worker。
在线状态生命周期 · 四态状态机
优雅断开
CS 收到 close → 删本机连接表 + del kv（先删本机，后删 kv；投递失败有 not-found 兑底）
异常残留
CS 宕机/断电 → kv 残留成 GHOST → 对账任务比对 kv.cs ∈ etcd 存活服务表，不等则清
漂移窗口
重连到新 CS 先 upsert 新值（覆盖旧值）→ 旧 CS 的 del 晚到也不删新记录（version 比较或幂等覆盖）
读写职责与三道失效防线（规避失效地狱）
角色对 online:{uid}本地缓存
Joker (CS)唯一写者：建立 upsert / 断开 del仅本机连接表 sync.Map（权威子集，无失效问题）
PG kv权威单点存储—
Delivery Worker只读（投递前查路由）30s TTL（副本方 N=2，全系统仅此两份）
网关 / feed-api不接触—
三道防线（事件可丢、缓存可旧，但过期有上界）： ① TTL 上界 30s——Worker 缓存最旧不超 30s，不依赖事件可靠； ② not-found 即时校正——投到已断开的 CS → 回 not-found → Worker 强制查权威值重投，错误视图存活 = 一次失败投递； ③ LISTEN/NOTIFY 加速（可选）——只用来缩短窗口，丢了无害，不是正确性依赖。 对比 etcd 方案：watch 断线重连需全量重建、多副本事件乱序不可判定——副本方越多地狱越深，本设计副本方 N=2 且有兑底。
对账兑底（双端两条）
服务端 · GHOST 清理任务（每 60s）
  • 扫描 kv online:* → 解析 cs 标识 → 比对 etcd 存活服务表（lease 60s）
  • cs 不在存活表 → 该记录为 GHOST → 删除（用户重连会重新 upsert）
  • 窗口最坏 = lease 过期(60s) + 扫描周期(60s) ≈ 2 分钟，投递错误由防线②即时修正
客户端 · seq gap 检查（心跳携带）
  • 客户端每 30s 心跳带 {conv_id, last_seq} → CS 比对 PG/kv 的最新 seq
  • 发现 gap → 推「有新消息」信号 → 客户端经网关 REST 按 seq 游标补拉
  • 这是推/拉两种投递模式共同的终极兑底：任何丢推/乱序/重连都能自愈
投递侧判定 Kafka chat.notify Push Worker + 厂商通道 在线分支（§3）
Push Worker 节流策略（可退房）
策略规则目的
同人合并同一 to_uid 60s 窗口内多条通知合并为一条（badge 累加）防轰炸
夜间静默23:00–08:00 除 @ 我/置顶会话外不推送（客户端时区）体验
频控单设备 ≤20 条/小时，超限只保 badge厂商配额 + 防封
失败退避厂商通道 429/5xx → 指数退避，3 次后入 notify.dlq隔离故障

容量：离线占比按 30% 估算 → 峰值 ~180 TPS 通知 → 单 Push Worker 余量充足；topic 仅 3P（key=to_uid 合并友好）。

05群聊系统设计

约束驱动的极简设计：≤500 成员 · 投递层写扩散 · 群内 seq 自增 · @ + 群主@all · 群管理五件套。零新增服务，群语义终结在 Delivery Worker 之前，Chat Server 仍是傻管道。
9 条约束 → 设计映射
约束落地设计
① 成员 < 500拉人时事务内 COUNT(group_members) 校验上限；500 在线成员的扇出在容量账内（§7）
② 写扩散投递层写扩散：persist 落库 1 份 → 批量查 online kv → 对在线成员逐个 produce chat.push（1:M）；存储不扩散——无未读/已读需求，读取按会话 seq 拉取，避免 500 倍存储放大
③ 未读数不实现无 unread 表与计数；客户端用本地 last_seq 自行渲染红点（服务端不背账）
④ 已读/撤回不实现无已读回执、无 revoke 标记；ACK 语义止步于「送达」（复用单聊 chat.ack）
⑤ 仅群主/普通成员role ∈ {owner, member} 二值；管理操作 owner-only 白名单（见权限矩阵）
⑥ @ + 群主@allcontent.mentions=[uid]，mention_all 布尔；persist 事务内权威校验 @all → role=owner（CS 仅做格式快检）
⑦ 新成员只看加入后group_members.joined_at；历史拉取 WHERE created_at ≥ joined_at（被踢者以 left_at 截止）
⑧ 群内消息 ID 自增复用单聊机制零改动：kv seq:{gid} 事务内自增 + messages UNIQUE(gid, seq)；seq 即群内消息 ID
⑨ 群管理五件套踢人/解散/改名/公告/置顶全部走网关 REST；群事件即消息（type=system_event 写入消息流，同链路扇出，seq 保序）
明确不做（诚实边界，写进 README）：未读数 · 已读回执 · 消息撤回 · 管理员角色 · 普通成员拉人（假设：入群仅群主操作，可调）· 群主退群（只能解散，不做转让）· 禁言/入群审批/群头像。约束 ③④ 省掉的是群聊最贵的两块状态——已读矩阵（N×M 写入）与撤回回溯，这是本设计敢在 3×4C16G 上跑群聊的前提。

群事件即消息：管理操作在事务里同时 ①改 group 表 ②INSERT 一条 type=system_event 消息（content={event, actor, ...}）→ 走同一条 persist→push 扇出链路。 成员打开会话即见「xxx 把 xxx 移出了群聊」，且事件与普通消息共享 seq 流天然保序——不用发明第二条通知通道。解散是特例：发完 dismiss 事件后 persist 拒收该 gid 一切后续消息。
@ 机制 · 数据结构与校验链
messages.content JSONB（群消息）:
{
  "text": "@张三 周末爬山吗",
  "mentions": ["uid-zhang"],
  "mention_all": false
}
  • CS 快检（格式层）：mentions 数组长度 ≤50、mention_all 布尔——非法直接回 ParameterIllegal，不进 Kafka
  • persist 权威校验（事务层）：mention_all=true → sender.role=owner；mentions 中每个 uid ∈ 当前群成员——失败整条拒绝（不留半条消息）
  • 投递展开：mention_all → 扇出时全员 mention=true；被 @ 成员的 chat.push 带 mention:true，客户端 UI 强提醒（无额外推送通道）
边界场景速查
  • 新成员历史：created_at ∈ [joined_at, left_at|now)——加入前的消息、被踢后的消息都不可见
  • 被踢瞬间在途消息：persist 校验按事务串行——left_at 已写则该成员不再进入扇出列表，无「被踢还收到消息」
  • 500 上限：拉人事务内 COUNT 校验，超限回 409
  • @all 大群风暴：500 在线 ×1KB = 500KB/条扇出，容量账（§7）覆盖；@all 不额外放大（本来就是全员扇出）

06朋友圈链路 · 新闻流系统

Gateway（鉴权/路由，不碰数据面） Feed API（发布同步返回） Kafka 异步 fanout PG 写/读 big_v pull 降级
