Alfred Brave — 分布式 IM 系统架构全景

基于 Go 1.21 + Gin + gorilla/websocket + etcd 的分布式即时通讯系统。
同一个二进制 (brave) 通过 urfave/cli 派生出 4 个子命令，启动为不同服务： start(业务 HTTP API)、joker(WebSocket IM 内核)、 cloudware(服务注册中心 shell)、migration(pressly/goose 数据库迁移)。

01部署拓扑

docker-compose: 1×mysql + 3×work (etcd 集群成员 + joker) + 1×server。三个 work 节点 = 三个独立 Joker 进程 + 三个 etcd 进程。
Server (brave start) Joker (brave joker · 3×) etcd v3.5.5 (3-node cluster) MySQL 8 (GORM) Cloudware (CLI shell, 当前空壳) Client (HTTP / WebSocket)

03三服务内部架构

所有服务的统一模板：gin.New() + 注册 routes + http.Server{Addr,Handler} + 后台 goroutines (Watcher / Controller / Lease)。

Server

业务 HTTP · :37001
brave start

用户系统 + 服务发现消费者：

  • POST /v1/register bcrypt 加密写 MySQL
  • POST /v1/login 校验密码 → 随机选 Joker → POST http://<joker>/login → 写 etcd 用户态 → 返回 LoginHost
  • GET /v1/user/:id GORM 查 user + friend 列表
  • 后台 goroutine StartListenService：每 5s 拉 etcd 的 services/* 刷新 api.Services
框架
Gin v1.8.1
ORM
jinzhu/gorm v1.9.1
客户端
internal/http_client (包装 net/http)

Joker

WebSocket IM 内核 · :37002
brave joker

每个 Joker 节点都是完整的 IM worker：

  • POST /v1/login 落 etcd 用户态（login_host / joker_service_id）
  • GET /v1/ws/:id upgrade → NewClient → 注册到 Manager
  • 每个 Client 启 2 个 goroutine：ReadPump + WritePump
  • Manager.Start() 消费三个 channel：Register / Unregister / Broadcast，Users 用 sync.Map
  • 启动即向 etcd putKeyWithLease(60s) + KeepAlive，注册本节点地址
WS
gorilla/websocket v1.5.1
并发
sync.Map + channel events
在线状态
etcd users/{uid} (JSON)

Cloudware

服务注册中心
brave cloudware

对外抽象：HTTP 注册中心（备选 gRPC）。当前实现状态见 部分完成 ：

  • POST /v1/services 写入 etcd 空壳 c.JSON(200,nil)
  • GET /v1/services 随机获取一个服务 空壳
  • GET /v1/services/:name 列出指定服务 空壳
  • 实际服务发现由 Joker/Server 直连 etcd 完成，Cloudware 的 HTTP 端并未被任何调用方使用

决策点 三个空壳：补完 OR 删掉改走 Nginx upstream（参见 AGENTS.md §6.P1）
