# Brave IM · DAU 容量战役报告（S3 → S3c → S3d，2026-09-08 收官）

> 硬件：3×4C15G 腾讯云 CVM 混部（每台 etcd+kafka；PG18 原生 node-1；gateway/cs/worker 分摊）。
> 连接轴基线：S1 已验证 501,752 稳态 / 71 万建连（[findings.md](findings.md)）。
> 本报告覆盖消息轴全战役：瓶颈定位 → 批量化改造 → 投递链修复 → 冻结口径终测 → DAU 结论与单聊/群聊配比。
> 判读口径遵循 [stress-plan.md §1.3.1](../../stress-plan.md)：**TPS 是事实，DAU 是估值**。

## 1. 压测动线与问题复盘

### 1.1 战役动线总览

```
S3 基线（09-08 凌晨）      单条串行消费模型 → persist 205 / deliver 117，DAU ≈1-2 万
   │
S3c 批量化（09-08 白天）   L1 批拉批写 → 651 TPS；L2 五句 SQL → 23505 crash-loop 卡壳
   │                       交接后：复盘复现 → 修 kv key 前缀 → StepA/A′ 阶梯
   │                       发现：单热分区 / ack 串行税 / CPU 墙 / 工具墙 / echo 污染
   │
S3d 投递修复（09-08 晚）   persist 批幂等 / ack 共享组路由 / Batch Relay + 6 实例
   │                       send_full 遥测 / stress 并行发送 + per-message ack
   │
终测（冻结口径）           单向 3500/s ×10min @9 万连接 → 全绿收官 → DAU 反推
```

### 1.2 问题清单与解决（按发现顺序）

| # | 问题 | 现象 | 根因 | 解决 | 验证 |
|---|---|---|---|---|---|
| P1 | **persist 23505 crash-loop**（S3c 最大障碍） | 干净 smoke 触发 `uq_messages_conv_seq` 冲突，worker 每 30s 崩溃重启；每次重启把 Kafka 组拖进 rebalance 风暴，12 消费者全部失去分区 → 全链冻结 | 批路径 kv key 写成裸 conv_id，`substring(k from 5)` 把 UUID 前削 4 位 → nextAfter 查不中 → seq 算出 0/负数 | `SELECT 'seq:' \|\| k`（一行）；清理 131 个裸键 + 234 行 seq≤0 + 计数器 heal | 500 条毒积压自排零错误；smoke lost=0 |
| P2 | **produce 空键单热分区** | chat.msg 12 分区只有 P3 有数据；S3"2→12 消费者不涨"的真因是 11 个消费者没活干 | 客户端不带 conv_id → CS 透传空串当 Kafka key | 单聊 conv 空时用 `single_key(from,to)` 作分区键（确定性/零查库/同会话保序） | 终测 12 分区均摊 |
| P3 | **deliver ack 串行税** | StepA 实测 deliver 只有 230/s（node-3 CPU 才 20%） | 每条送达同步 produce 一次 acks=all | 送达批内累积、批尾一次 WriteBatch | 230 → ~5100/s |
| P4 | **ack 广播消费**（3500 档 ack p50≈14s） | 每台 CS 用独立消费组串行吃全量 chat.ack，单条 fetch+commit | 架构：组=ServiceId 随机 UUID | 共享组 `cs-ack` + 批拉批提交 + `GetMany` 批查 online + 本机直写/异机 `BatchRelayAcks` 批转发；StartOffset=LastOffset | ack p50 14s → **650ms** |
| P5 | **单 deliver + 每条 unary RPC** | 16 分片下 deliver ~4k/s 而 CPU 仅 20%（延迟墙）；批提交被最慢 RPC 卡住 | 每条消息一次跨机 unary，64 分片也吃不满 | proto 增 `BatchRelayMessages/Acks`（保持 Unary，逐条结果）；deliver 按目标 CS 聚批，失败逐条回退；`brave-deliver@.service` ×6 实例共享组 | 终测全程 send_full=0 |
| P6 | **慢消费 3s 阻塞** | relay 写 Send 通道最多等 3s，一个慢客户端拖住 512 条批次 | 阻塞式 select | 改立即非阻塞判定（满即 `send_full`），+原子计数 +`/debug/relay` 端点 + collect.sh 采集 | 慢消费隔离且可观测 |
| P7 | **Kafka 重试重复帧烧 seq** | 8-sender 档客户端 ~5k/s 但 Kafka offset 7518/s；PG `mid` 全唯一（行没重复） | acks=all 超时重试是 at-least-once；persist 批路径**先烧 seq 再 `ON CONFLICT DO NOTHING`**，重复帧留下 seq 空洞 + 重复扇出 | `handleSingleBatch` 在 seq 分配前：批内 msg_id 去重 + 一次查已落库重放（复用原 seq 补投 push） | 终测 PG 新增行=发送数分毫不差 |
| P8 | **压测工具发送墙** | 配置 5000/8000 实际只有 3504/4521/s | 旧版单 goroutine 串行 JSON+WS 写 | `-send-workers N` 固定连接分片并行（每连接单写协程，满足 gorilla 约束） | 高档位测量有效化 |
| P9 | **echo 模式污染测量** | Kafka 流入≈2×用户消息；客户端 lost 统计有假丢失 | 回显把每条消息变两条 Kafka 消息；账本按 conv 全局 lastSeq 被双向接收方交叉更新（ooo 假阳性） | 容量判读只允许单向 storm；echo 仅正确性冒烟；报告固定口径注记 | 单向 smoke lost=0/ack 100% |
| P10 | **部署脚本误杀 PG** | 每次部署后 PG 57P03 重启 | `pkill -f "[b]rave "` 匹配了 PG backend 命令行（`postgres: 18/main: brave`） | 锚定 `^/usr/local/bin/brave ` | 后续部署 PG 零误伤 |
| P11 | **Kafka 组 rebalance 僵局** | 13 成员全部 0 分区、组卡 PreparingRebalance、reset-offsets 被拒 | crash-loop 的反复加入 + 僵尸会话 | 修掉 crash 根因（P1）+ 等会话过期后组归 Empty 再操作 | 组 Stable 12/6 成员 |
| P12 | **notify 逐条生产** | 全离线清积压时 deliver 被钉回 ~200/s | offline 分支每条一次 acks=all produce | offline 通知同款批写（`SetBatchOfflineHook`） | 219 万积压 ~6 分钟排空 |

经验教训（写进 [stress-plan §1.3.1](../../stress-plan.md)）：批路径 SQL 必须与单条路径共用同一 key/幂等约定；诊断日志带 conv#seq sample + nextAfter map 是快速定位的关键；先修幂等再打压测，否则数据不可信。

## 3. 结论与估算

### 3.1 TPS 事实表（实测钉死）

| 链路 | D13·1万基准 | D13·30万需求 | **实测** | 达成率 |
|---|---:|---:|---|---:|
| persist 落库峰值 | 120 | 3600 | **3435–3495/s 稳态** | 96% |
| 投递峰值（单聊 1:1） | 81 | 2400 | **3435–3495/s**（99.89%） | 146% |
| 投递峰值（群扇出 1:15） | 520 | 15600 | **未测** | — |
| 离线通知峰值 | 180 | 5400 | 半测（~6k/s 生产侧观测） | — |
| ACK | — | — | 3435/s 下 99.89%，p50=650ms | — |

### 3.2 DAU 反推（TPS × 系数 → 估值）

公式：人均 50 条/天；×20 峰值系数 DAU = T×86.4，×10 = T×172.8。

| 用哪个 T | ×20 保守 | ×10 社交真实 | 判据表落点 |
|---|---:|---:|---|
| S3 改造前 205 | 1.8 万 | 3.5 万 | 降档 10 万级以下 |
| **终测 3435（窗口均值；稳态瞬时 3495）** | **29.7 万** | **59.4 万** | T∈[1.8k,3.6k] → **×10 平均口径 30 万成立** |

诚实表述：**能对外钉死的事实是"单向 3500/s 端到端（投递+ACK）稳定"**；DAU 按口径反推给区间。×20 按精确系数算得 29.7 万（按判据表保守锚 120 TPS/万 则为 28.6 万），但预注册判据线是 T≥3600 → **×20 全包络不宣称**。

### 3.3 单聊 × 群聊组合：甜点区

成本模型：群消息落库 ×1（存 1 份）、投递 ×F（F = 在线成员数；50 人群 × 30% 在线 = **15**）。
容量公式：**T(g) = min(P, D ÷ (1 + 14g))**，g = 群消息占比。

| 群占比 g | 总消息 T | 单聊/s | 群聊/s | DAU ×20 | DAU ×10 | 判定 |
|---:|---:|---:|---:|---:|---:|---|
| 0% | 3435 | 3435 | 0 | 29.7 万 | 59.4 万 | 吞吐极限 |
| 2% | 2684 | 2630 | 54 | 23.2 万 | 46.4 万 | ×20/30万已不可达（注①） |
| **5%** | 2021 | 1919 | 101 | 17.5 万 | 34.9 万 | **甜点区起点：15% 余量保 30 万×10** |
| **7%** | 1735 | 1613 | 121 | 15.0 万 | **30.0 万** | **30 万×10 名义临界** |
| 10% | 1431 | 1288 | 143 | 12.4 万 | 24.7 万 | 甜点区边界 |
| 15% | 1108 | 942 | 166 | 9.6 万 | 19.1 万 | 群体验换 DAU 半价 |
| 30%（D13 假设） | 661 | 462 | 198 | 5.7 万 | 11.4 万 | 群重场景 |
| 100% | 229 | 0 | 229 | 2.0 万 | 4.0 万 | 纯群聊极限 |

注①：30 万 ×20 需峰值 T=3472 > 纯单聊极限 3435——**当前硬件无解，与配比无关**。

**甜点区解读**：
- 边际成本在低占比时最贵：0%→1% 损失约 480 msg/s 总容量，20%→21% 只损失 ~18。前几个百分点的群聊最贵。
- **甜点区 = 群占比 5%–10%**：5% 留 15% 反压余量保 30 万×10；10% 用 24.7 万×10 换可感知群功能；>10% 后每点 DAU 掉 2 万+。

### 3.4 锁定 30 万 DAU 的最佳配额

| 口径 | 可行性 | 最佳群占比 | 单聊配额 | 群聊配额 | 投递占用 | 建议 |
|---|---|---:|---:|---:|---:|---|
| ×10 | ✅ | 名义 **7%** | 1615/s | 122/s | 100% 打满 | 无余量 |
| **×10 + 15% 余量（推荐）** | ✅ | **5%** | **1649/s** | **87/s** | 86% | **稳健配额** |
| ×20 | ❌ | 当前不可达 | — | — | — | 拓扑解耦后（D≈4500）g≤2.2% |

推荐配额（g=5%）产品语言：总消息 1500 万条/天 = **单聊 1425 万 + 群聊 75 万**；峰值 1736 msg/s 中单聊 1649 + 群聊 87；同时活跃群（假设高峰 30s/条）≈2600 个 50 人群（按日均 200 条/群 ≈3750 个）。

### 3.5 提升群聊占比的杠杆（按性价比）

1. **ACK 去重**（小改）：群消息当前给发送者回 15 条重复 ack（按 push 逐条回），同批同 msg_id 折成 1 条即可白捡流量。
2. **拓扑解耦**（部署）：PG 独立机 / 外置 driver → D 3435→4500+，全表右移 ~30%，30 万×10 群占比临界 7%→13%；×20/30 万变为可达（g≤2.2%）。
3. **群投递换模型**（架构）：群消息不逐成员 push，改"会话级通知 + 客户端拉取"，投递成本 F→1，30% 群占比下总容量回到 ~3435/s（≈29.7 万×20 DAU）。这是大群场景的通用取舍（写扩散→读扩散/混合）。
